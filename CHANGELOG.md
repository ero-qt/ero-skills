## [Unreleased]

### Added

- `repo-writing` skill, which writes commits, PRs, issues, review replies and docs the way a person on GitHub would, after it reads the repo's own style. It starts from how natural text reads, with 3 tests to run on every draft. Its list of AI tells goes from single words up to the stance of a whole text. The prose check flags most of them, reads whole paragraphs for rhythm and prints how many tells it found per 100 words. `--explain` prints why a rule flags a sentence and how to fix it.
- `code-comments` skill, which makes code explain itself and keeps comments to the facts that the code can't show.
- `terse-replies` skill, which keeps chat replies caveman-short at 3 levels, with the answer first, exact steps and the state and next step at the end. Its plugin also sets a Terse output style, and a hook that reminds Claude of the level in 1 line at every prompt, so the style stays on for the whole session. The full rules come back after a compaction and at the prompt after a reply that broke one of them. The level is kept between sessions. At the end of each turn a check reads the reply and writes every broken rule to `slips.jsonl` in the plugin's data folder, like a commit gate longer than 12 lines, a dash or a closing offer. It never stops the turn.
- `work-loop` skill, which runs repo tasks in one fixed order, from checking open PRs and issues to the review and the PR. Each commit gets a size from trivial to large and a loop level of `light`, `standard` or `strict`. The 2 together pick the steps it runs. A rename skips the review. A new public type gets a plan of several commits first. Each step that an agent runs has its brief in `stage-briefs.md`, and `stages.md` gives the ledger record of every step. The rules of a repo go in a house brief at `.git/work-loop/house.md` that every agent reads. After a crash or a compaction, a commit goes on at the first step without a record. Its `commit-cycle` workflow runs the agent steps of 1 commit in order, with the review agents at the same time, and returns the ledger records. It stops at the first step without a proof, like a red test that passes, and a stopped run goes on from the step it stopped at. The commit gate fits in 12 lines, with all checks on 1 line and the subject right above `Approve?`. Choices that differ from person to person, like the loop level, the issue step, the review model or deleting merged branches, are knobs in `.git/work-loop/knobs.json`. Each knob has a default, so you don't have to set any. Its `ledger.js` script writes the proof of each step of a commit to `.git/work-loop/ledger.jsonl`, where it can't be staged by mistake. Its plugin checks every `git commit` before it runs. It stops a commit with a trailer in the message, a hard finding of the prose check or a staged path from the never-stage list (`.env`, `.claude/settings.local.json` and the lines of `.git/work-loop/never-stage`). It also stops a command that stages files and commits in one go, like `git add -A && git commit` or `git commit -a`, because the checks read the staged files before the command runs. Staged text that belongs to someone else, like a license, can keep what the prose check flags when the ledger gives a reason. When source changes without a doc change and the ledger doesn't say why, it warns Claude. It stops the commit instead when `.git/work-loop/knobs.json` sets `"loop": "strict"`. Each finding goes to `slips.jsonl` in the plugin's data folder.
